## 一、Why（为什么做）

### 1.1 业务背景

Team Portal Lite 是一个面向**大型企业客服部门**的 B2B SaaS 工单管理系统前端（产品代号"高级接单台"）。

**业务规模：**

| 指标 | 数值 |
|------|------|
| 付费企业客户 | 5000+ 家 |
| 累计客服人员 | 100 万人 |
| 日活跃用户（DAU） | 30 万 |
| 单租户历史工单量 | 最高 10 万条 |

**核心业务痛点：**

- 大型企业客服部门每日处理海量工单，需要高并发、高可用的工作台支撑。
- 不同企业客户有强烈的品牌定制诉求（主题色、Logo、布局风格），需要多租户动态换肤能力。
- 客服人员需要实时接收新工单/客户消息，不能依赖页面刷新。
- 10 万条历史工单需要流畅浏览，不能出现卡顿或内存溢出。
- 客服人员在平板和大屏之间切换办公，界面必须自适应。
- 企业客户分布在不同国家/地区，需要多语言支持。

本项目需复刻**真实高并发、高可用的企业级 SaaS 工程环境**，而非 Demo 级玩具项目。

### 1.2 个人成长目标

本项目作为**简历核心项目**，目标是打造：

- **大厂 P6/P7 级敲门砖**：体现从架构决策到工程落地的完整闭环能力。
- **创业 Lead 的核心竞争力筹码**：证明能独立主导复杂前端项目的技术选型与交付。

**可量化成果目标：**

| 指标 | 目标值 | 衡量方式 |
|------|--------|----------|
| Lighthouse 性能分 | ≥ 96 | Lighthouse CI 自动化检测，PR 阻断 |
| TypeScript 严格模式 | 0 个 `any` | `strict: true` + ESLint `no-explicit-any` CI 阻断 |
| 测试覆盖率 | ≥ 75% | Vitest 单测 + Playwright E2E，覆盖率聚合 |
| 大数据列表滚动帧率 | ≥ 50fps | 10 万条数据下性能测试 |
| WebSocket 消息延迟 | ≤ 100ms | 从接收到 UI 展示的端到端延迟 |

### 1.3 核心价值定位

- **对业务**：提供多租户隔离、实时响应、大数据量流畅操作的客服工作台。
- **对工程**：验证 Monorepo + RSC + 设计 Token 体系在大型 SaaS 场景下的可行性。
- **对个人**：形成从架构决策到工程落地的完整闭环能力证明。

## 二、Who（给谁用）

### 2.1 角色一：付费企业客户（管理方）

**身份**：企业客服部门的管理者、IT 管理员、决策者。

**核心诉求**：

1. **品牌定制**：希望工作台贴合企业品牌形象（主色、Logo、配色方案），提升客服人员的企业归属感。
2. **多租户隔离**：确保本企业的数据、配置、主题与其他企业完全隔离，数据安全合规。
3. **管理概览**：通过 Dashboard 查看工单统计概览（工单量、响应时长、解决率等），掌握团队运营状况。
4. **团队配置**：管理客服人员分配、工单优先级设置、工作流配置。
5. **系统稳定性**：要求系统高可用，不能因为高峰期卡顿影响客服团队效率。

### 2.2 角色二：最终客服用户（使用方）

**身份**：企业客服部门的一线客服人员，日常使用工作台处理工单。

**核心诉求**：

1. **高效处理工单**：快速查看工单列表、筛选搜索目标工单、查看详情、流转状态（待处理→处理中→已解决→已关闭）。
2. **实时消息提醒**：客户发来新工单/投诉时，立刻收到通知，不遗漏任何客户请求。
3. **流畅浏览历史工单**：面对上万条历史工单，能快速滚动、定位、查找，不卡顿。
4. **多设备适配**：在公司用大屏、在家用平板，界面都能正常操作。
5. **母语操作**：界面使用熟悉的语言（中/英/日等），日期、数字格式符合本地习惯。
6. **低学习成本**：界面直观一致，设计系统统一，减少认知负担。

## 三、What（做什么）

### 3.1 必须交付的核心功能范围

#### 功能一：多租户动态主题系统

- 支持按租户（企业客户）动态切换品牌主题（如 A 公司蓝+白，B 公司红+金）。
- 主题切换无需全局重新渲染，通过 CSS 变量 + Design Token 体系实现运行时换肤。
- 每个租户可自定义主色、辅助色、圆角、间距等基础 Token。
- 主题切换无 FOUC 闪烁（内联脚本提前注入 CSS 变量）。

#### 功能二：实时通知系统

- 基于 WebSocket 实现工单消息实时推送。
- 客户发来投诉/新工单时，客服端立刻弹出新消息提醒，不依赖页面刷新。
- 包含通知中心、未读计数、消息已读状态同步。
- 心跳保活 + 指数退避重连，重连后同步离线消息。
- 多标签页消息共享（BroadcastChannel / SharedWorker），避免重复消费。

#### 功能三：大数据虚拟滚动列表

- 单个大型客户可能拥有 10 万条历史工单，需支持流畅浏览。
- 采用虚拟滚动技术（`@tanstack/react-virtual` dynamic 模式），仅渲染视口内可见数据。
- 支持动态行高（工单内容长度不一），提前测量/估算行高。
- 筛选/搜索后保持滚动位置，不重置到顶部。
- 滚动时正确清理事件监听与缓存，防止内存泄漏。
- 滚动帧率 ≥ 50fps。

#### 功能四：响应式适配

- 覆盖移动端（平板）→ 桌面端（大屏）的断点体系。
- 布局、导航、表格密度随屏幕尺寸自适应调整。
- 客服在家用平板、在公司用大屏幕，界面均需自动适配。

#### 功能五：国际化（i18n）

- 界面支持 5 种语言：中文、英文、日文等。
- 文案、日期格式、数字格式、RTL 方向（如涉及）均需本地化处理。
- 语言切换不丢失当前操作状态。

#### 功能六：工单核心业务流程

- 工单列表展示、筛选、排序、搜索。
- 工单详情查看与状态流转（待处理→处理中→已解决→已关闭）。
- 客服分配、优先级标记、内部备注。
- 工单统计概览 Dashboard。

### 3.2 五大核心挑战确认

以下五大核心挑战**全部在交付范围内**，不得裁剪：

| # | 挑战 | 技术方案 |
|---|------|----------|
| 1 | 多租户动态主题 | CSS 变量 + Design Token + Tailwind 双层管理 |
| 2 | 实时通知 | WebSocket + 心跳保活 + 指数退避重连 + 批量更新 |
| 3 | 虚拟滚动 | `@tanstack/react-virtual` dynamic 模式 |
| 4 | 响应式适配 | Tailwind 断点体系 + 自适应布局/表格密度 |
| 5 | 国际化 | i18n 方案 + 文案/日期/数字本地化 + 状态保持 |

## 四、How（怎么做）

### 4.1 整体技术路线

#### 框架与架构

| 层面 | 技术选型 | 说明 |
|------|----------|------|
| 前端框架 | **Next.js 14** + React Server Components (RSC) + App Router | 必须使用 App Router，禁止 Pages Router；充分利用 RSC 减少客户端 JS 体积 |
| Monorepo | **pnpm** + **Turborepo** | 5 Apps + 10 Packages，禁止混用 npm/yarn，禁止 Lerna |
| UI 技术栈 | **Radix UI** + **Tailwind CSS** + **shadcn/ui** | 禁止 Ant Design / Element UI；禁止 CSS-in-JS |
| 样式方案 | Tailwind + CSS 变量 | Design Token 通过 Tailwind 配置 + CSS 变量双层管理 |
| 客户端状态 | **Zustand** | 仅管理 UI 状态（弹窗开关、表单草稿） |
| 服务端状态 | **TanStack Query**（React Query） | API 数据一律走 TanStack Query，禁止用 Zustand 存服务端数据 |
| 单元测试 | **Vitest** | 禁止 Jest |
| E2E 测试 | **Playwright** | 禁止 Cypress |
| 部署平台 | **Vercel** | 禁止自建 Nginx/Node 服务器 |
| CI 性能检测 | **Lighthouse CI** | 每次 PR 自动运行，不达标阻断合并 |

#### 代码质量铁律

- TypeScript `strict: true`，**0 个 `any`**，ESLint `@typescript-eslint/no-explicit-any` CI 阻断。
- 测试覆盖率 ≥ 75%，核心业务流程必须有 Playwright E2E 覆盖，组件必须有交互测试（非仅快照）。
- 设计 Token 命名全局统一（如 `--color-primary-500`），禁止硬编码颜色/尺寸值，ESLint 规则扫描。
- Packages 之间禁止循环依赖，madge 在 CI 中检测。
- 提交前必须通过 ESLint、Prettier、TypeScript 类型检查、测试全量通过。

### 4.2 POC 验证计划

在大规模开发前，先跑通最小原型验证基建可行性：

1. **POC-1**：1 个 App + 1 个 Package 的 Monorepo 构建与引用，验证 pnpm + Turborepo + 路径别名。
2. **POC-2**：RSC + Client Component 边界验证，确认 "use client" 指令与 Zustand/TanStack Query 协作正常。
3. **POC-3**：CSS 变量 + Tailwind 双层 Token 体系，验证运行时动态换肤无 FOUC。

POC 验证通过后，再批量创建剩余 Apps/Packages 并投入大规模开发。

### 4.3 脚手架脚本规划

将 Monorepo 初始化步骤固化为脚手架脚本（如 `scripts/init-monorepo.js`），确保：

- 自动生成 5 Apps + 10 Packages 目录结构与 `package.json`。
- 自动生成 `pnpm-workspace.yaml`、`turbo.json`、根 `tsconfig.json` paths 配置。
- 包名（`@team-portal/xxx`）与导入路径严格对应，杜绝路径别名配置错误。
- 可重复执行，确保任何人 clone 后都能一键初始化。
